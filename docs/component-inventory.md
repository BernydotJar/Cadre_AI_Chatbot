# Component inventory

Core source inspection began 2026-09-08; this inventory was reconciled 2026-09-09 after the product-polish, Chrome, CI/CD and n8n workstreams. This inventory satisfies the component-documentation portion of [T-N6-3](../specs/001-support-chatbot/tasks.md). It describes the implemented application and its verification surfaces; it does not establish that the current source is deployed, the live evaluation has passed, the source archive is complete, or release closure is approved. Current execution belongs in the checkpoint and graph evidence, not this inventory.

The application is one Next.js App Router project with a browser UI and a Node.js chat endpoint. The following boundaries are implemented in source:

| Component | Main source | Contract and responsibility |
| --- | --- | --- |
| Client configuration | [cadre.ts](../src/config/cadre.ts), [types.ts](../src/config/types.ts) | Versioned brand, six topics, approved facts/links, provenance and boundary phrases → validated `ClientConfig`. |
| Conversation core | [src/core](../src/core/) | Unknown request data and validated messages/config → validation result, topic decision and deterministic reply policy. No network or React. |
| Provider adapter | [src/provider](../src/provider/) | Routed entry and bounded conversation → approved fact indices or a typed error. Owns mock/OpenRouter translation and budget checks. |
| Server and HTTP routes | [chat.ts](../src/server/chat.ts), [app/api](../app/api/) | HTTP request → bounded `{ reply, kind }`; owns admission, streamed-body limits, orchestration and safe error translation. |
| Browser UI and server page | [support-chat.tsx](../src/ui/support-chat.tsx), [page.tsx](../app/page.tsx) | Safe server props and API responses → local conversation state, text/approved links, keyboard/mobile controls and recovery. |
| Engineering process adapter | [tools/graph-adapter](../tools/graph-adapter/) | Approved node definitions and CLI arguments → pinned external Graph Harness commands and retained check outputs. Outside the chatbot runtime. |
| Chrome Integration Preview | [extension](../extension/) | Optional fixed-origin launcher/panel/transport adapter using the same chat API; URL-only presentation context. |
| CI/CD | [.github/workflows](../.github/workflows/) | Secret-free verification and gated exact-SHA delivery to the existing Vercel project. |
| n8n handoff contract | [integrations/n8n](../integrations/n8n/) | Optional consent-checked structured handoff webhook contract; no real recipient/credential is embedded. |

For a chat request, the server applies admission and JSON/schema validation, then routes using the full validated history. Clarification, refusal and unsupported/account-specific replies are deterministic. Only a grounded decision calls the fact selector. The server renders the selected facts first, appends every remaining fact from that entry, and adds the entry's approved links. The model does not compose unchecked business prose or choose new destinations.

## 1. Client configuration and knowledge

**Contract and configuration surface.** `ClientConfig` supplies `clientName`, `botName`, `tagline`, `officialDomain`, a contact link, knowledge entries and boundary copy/phrases. Each `KnowledgeEntry` contains an ID, topic, display label, routing keywords, fact strings, approved links, and `source.origin` with an optional retrieval date. The current Cadre entries all carry a date. Six entries group overview, industry fit, strategist contact, portal access, maturity assessment, and models/security; the [approved index](../specs/001-support-chatbot/README.md) explains the refinement from the original corpus-size estimate.

**Invariants.** Configuration is parsed and deep-frozen at module load. It rejects duplicate IDs/topics, cross-topic duplicate normalized keywords, empty normalized triggers, and exact boundary/keyword collisions. Approved link hosts must match the declared official hostname or a subdomain. These checks establish structure and ownership, not the truth of a fact or complete natural-language coverage. The UI separately requires an exact approved URL before making it clickable.

**Provenance.** Facts live in TypeScript and are versioned with source changes. Entry-level provenance distinguishes official pages from the company-provided profile. [The knowledge source audit](knowledge-source-audit.md) records page/section research and remaining gaps; research notes do not become runtime facts automatically. Current security and partnership wording attributes company claims, preserves unverified relationships/controls, and distinguishes Cadre's published privacy policy from this separately hosted chatbot. There is no runtime scraping, document ingestion, embedding index or vector database.

**Tests and maturity.** [Configuration tests](../tests/config/config.test.ts), [knowledge-refresh regressions](../tests/config/knowledge-refresh.test.ts), and core/API tests exercise structure, routing, retained boundaries and reply size. This is a curated MVP knowledge store requiring editorial refresh; passing tests cannot establish source freshness. [Acme Outdoors](../src/config/fixtures/acme.ts) is a fictional test fixture demonstrating core/config separation. It is not a second production client or evidence of production multi-client reuse. The page composition and some UI copy remain Cadre-specific.

## 2. Pure conversation core

**Contract and configuration surface.** [Validation](../src/core/validate.ts) returns an explicit success/error result from unknown input. [Routing](../src/core/route.ts) returns `match`, `ambiguous` or `unknown`; [policy](../src/core/policy.ts) maps validated messages and a supplied `ClientConfig` to `grounded`, `clarify`, `redirect` or `decline`. `composeReply` returns text, app-owned links and the policy kind. Shared constants are in [limits.ts](../src/core/limits.ts); [text.ts](../src/core/text.ts) owns normalization.

**Invariants.** Only user/assistant message roles are accepted, content must be nonempty after trimming, and the final message must be from the user. Account-specific and unverified-claim boundary triggers take precedence over topic scoring. Whole normalized phrases are scored with overlapping aliases counted once; tied leaders produce ambiguity. Canonical clarification can resolve a short ordinal against the immediately preceding exchange. User/assistant history never supplies new authoritative facts or links.

**Provenance, tests and maturity.** These are project-owned pure functions implementing S1–S6, with [validation](../tests/core/validate.test.ts), [routing](../tests/core/route.test.ts) and [policy](../tests/core/policy.test.ts) suites, including the second-client fixture. They are inspectable, bounded MVP logic, not semantic retrieval or an open-ended reasoning system. Unlisted paraphrases can miss a topic; mixed topics can require clarification. Clarification state arrives from the client and is forgeable: omitting or forging its marker can change clarify-versus-redirect behavior, but cannot add approved facts, links or account access. The UI retains the first clarification pair for normal session behavior; there is no server-side conversation store.

## 3. Provider adapter

**Contract and configuration surface.** [FactSelector](../src/provider/types.ts) exposes `selectFacts({ entry, messages, signal? }): Promise<readonly number[]>`. [MockFactSelector](../src/provider/mock.ts) returns the entry's indices locally. [OpenRouterFactSelector](../src/provider/openrouter.ts) uses built-in server fetch and validates both provider metadata and a strict JSON fact-index response. Its test seams are injected fetch and clock implementations.

[Configuration](../src/provider/config.ts) reads server-side `CHAT_PROVIDER`, `OPENROUTER_API_KEY`, optional `OPENROUTER_MODEL`, and `OPENROUTER_KEY_EXPIRES_AT`. The default is mock; invalid live configuration fails rather than silently selecting mock. The approved model constant is `openai/gpt-4.1-mini`; the operational deadline is capped at `2026-09-15T00:00:00Z`. Variable names are documented here, never credential values.

**Invariants.** Indices must be nonempty, unique integers within the routed entry. Provider prose, tool calls and URLs do not become answers. The adapter keeps at most ten recent messages and removes oldest history until the complete serialized prompt fits 32 KiB, retaining the final question, facts and system/schema content. Output is capped at 256 tokens, and incoming provider JSON is capped at 32 KiB. It retries at most once for an explicit 429/503 rejection, with at most a two-second delay; ambiguous network failures/timeouts and malformed successful responses do not retry automatically.

Key metadata must describe a non-resetting limit no greater than $5 with consistent remaining allowance/usage. Routing requests input/output price ceilings of $0.50/$2 per million tokens. Local reservations retain $0.50 and charge uncertain outcomes conservatively. Those counters are process-local and disappear on restart; the provider-enforced key limit is the intended cross-process hard ceiling. This inventory does not independently verify the current key allowance. Cancellation is not a refund guarantee.

**Provenance, tests and maturity.** The [provider decision](../progress/provider-decision.md) records the API/structured-output rationale and dated model observation. [Adapter tests](../tests/provider/openrouter.test.ts) use synthetic transport for request structure, Unicode/escaping limits, malformed output, errors, deadlines, retry and budget accounting. This is an implemented constrained adapter with mock coverage; current live-model availability, billing and behavior need separate dated evidence. The provider key is exclusively for chatbot inference, not coding assistance.

## 4. Server orchestration and public HTTP boundary

**Contract and configuration surface.** `POST /api/chat` accepts `{ messages: [{ role, content }] }` and returns `{ reply, kind }`. Successful policy kinds are `grounded`, `redirect`, `clarify` and `decline`; validation/transport/provider failures use `error` with an appropriate HTTP status. `GET /api/health` returns `{ status: "ok" }`; it does not test provider readiness. [createChatHandler](../src/server/chat.ts) accepts injected config, environment, selector, fetch, clock and limiter for tests. The [route](../app/api/chat/route.ts) selects Node.js runtime and delegates to that handler.

**Invariants and limits.** The API requires JSON content type, checks actual incoming UTF-8 bytes before full parsing, accepts at most 20 messages of 2,000 UTF-16 units each, and caps the raw body at 256 KiB. [I/O helpers](../src/server/io.ts) propagate cancellation and enforce a total 20-second deadline across body reading, provider preflight/inference and retry waiting. Replies are capped at 2,400 characters; the server fails rather than truncating a required fact or URL. Responses disable caching and return safe static failure copy instead of upstream exception bodies or credentials.

[RateLimiter](../src/server/rate-limit.ts) allows ten requests per 60-second fixed window. It tracks at most 1,024 clients and uses a shared overflow bucket afterward. `CHAT_TRUSTED_PROXY_IP_HEADER` permits only `x-forwarded-for` or `x-real-ip`, and only a single valid IP is accepted. Without that explicit trusted-ingress configuration, requests share a global bucket. Enabling the option is not proof that a host sanitizes the header. These controls reset with the process and are not distributed enforcement or authentication.

**Provenance, tests and maturity.** The orchestration is project-owned code implementing the approved API and provider decision, covered by [API integration tests](../tests/api/chat-route.test.ts) and [rate-limit tests](../tests/server/rate-limit.test.ts). It is an anonymous MVP endpoint with deliberate limits. Header behavior and anonymous roundtrips on a particular deployment require deployment evidence; local integration tests alone do not establish them.

## 5. UI, server composition and layout

**Contract and configuration surface.** The dynamic [server page](../app/page.tsx) derives a safe mock/live-configured/unavailable label, checks live configuration, and passes identity, topic labels, contact and exact approved links to `SupportChat`. It passes no credential or provider client. [conversation.ts](../src/ui/conversation.ts) owns request-history shaping, response validation and URL tokenization. [layout.tsx](../app/layout.tsx) owns page metadata/language and [globals.css](../app/globals.css) owns the responsive visual rules. Component props expose some client configuration; this is not a complete theme or multi-tenant administration API.

**Invariants.** React text nodes render message content; arbitrary HTML is not executed. Only exact approved URL tokens become anchors, with safe external-link attributes. Page memory holds at most 40 displayed messages, shapes outbound history to the API limits, and retains a clarification pair. No local/session storage or database persists the conversation. Refresh or reset clears this page's state; that does not promise deletion or zero retention by hosting/model services.

Submission owns a synchronous single-flight lock and operation identity. A server/initial-hydration readiness snapshot disables the textarea, Send and topics until client activation; no-JavaScript visitors retain guidance and contact navigation. Delayed-script/no-JavaScript regressions live in e2e/hydration.spec.ts. Stop, timeout, reset and retry preserve the relevant turn and reject stale output; the client timeout is 25 seconds. Enter sends, Shift+Enter inserts a line, and composition guards protect IME entry. Transient controls hand focus to the composer at activation, while reply arrival does not take focus. Empty welcome content starts at the top, reading position is preserved, and Jump appears only in an active conversation. The UI describes its scope and external-model processing without implying account access or a connected human handoff.

**Provenance, tests and maturity.** The UI is project-owned React/plain CSS with system fonts; its rationale is in [the UX assessment](chatbot-ux-assessment.md). [Helper tests](../tests/ui/conversation.test.ts) cover payload/rendering boundaries; [browser tests](../e2e/chat.spec.ts) cover real local mock flow and intercepted failures, keyboard/IME, cancellation/retry, reset, long history, scrolling and mobile layout. [Playwright configuration](../playwright.config.ts) separates a managed local mock server from an explicitly supplied external base URL. External-server cases can reach a live provider, so they are not automatically free mock checks. This is an implemented MVP interface with reviewed regressions; browser checks are not full accessibility certification or proof of current public/live delivery.

## 6. Engineering process adapter and evidence runner

**Contract and configuration surface.** Project-owned [nodes.mjs](../tools/graph-adapter/nodes.mjs) expresses the approved N1–N6 definitions. [generate.mjs](../tools/graph-adapter/generate.mjs) produces the initial project shape and refuses regeneration once the event ledger is nonempty. [graph.mjs](../tools/graph-adapter/graph.mjs) delegates CLI arguments to an external Graph Harness checkout selected by `GRAPH_HARNESS_RUNTIME`, using `GRAPH_PYTHON` or `python3`. It requires upstream revision `6a5f201e2bc640ac46cc0b4b6a3d11b788555664` with no tracked modifications. It is a thin bridge, not a vendored runtime or a chatbot dependency.

**Invariants.** The coordinator is the only Git/ledger writer. Mutating commands receive the current expected last event ID unless supplied; evidence recording requires an existing in-project artifact and a matching/computed SHA-256. These checks support the external runtime's lifecycle; they do not authorize a transition or make handwritten evidence trustworthy. The baseline is not mutable progress, and tools are not imported by the application.

[verify.mjs](../tools/graph-adapter/verify.mjs) runs actual local test/typecheck/lint/build commands in mock mode (`--quick` omits build), writes to a new `evidence/runs/<label>` directory, and refuses reused labels. It redacts project paths, terminal formatting and a known OpenRouter token pattern; this is not a universal secret scanner. Its exit status reflects command results, not independent review or release approval.

**Provenance, tests and maturity.** [Engineering workflow documentation](engineering-workflow.md) owns methodology and runtime provenance. [Baseline tests](../tests/tools/graph-baseline.test.ts) check shape, canonical nodes, dependencies, gates and the freeze guard. They do not fully exercise every CLI wrapper or upstream runtime behavior. This is repository-specific process tooling; actual command receipts, separate role reports and graph validation remain necessary evidence. Its presence does not prove that a native skill command or independent agent was executed.

## 7. Chrome Integration Preview

The optional Manifest V3 adapter lives under `extension/` and is not a second chatbot. It injects a style-isolated launcher only on approved Cadre origins, opens an extension-origin panel and transports validated requests to one fixed candidate API. The latest context feature maps an allowlisted pathname/hash to a small presentation enum; it does not read host-page text/forms/cookies/storage. Current evidence: 72 extension tests, 23 synthetic-browser checks and a 17-check disposable installed-site run on `cadre.ai/agents#discover-agents`, with all G9 gates PASS. See `docs/extension-preview-design.md` and `extension/README.md`.

## 8. GitHub CI and Vercel delivery

`.github/workflows/ci.yml` reproduces locked install, lint, typecheck, tests, build, Playwright and extension checks without deployment secrets. `.github/workflows/deploy-production.yml` requires the GitHub `production` environment plus existing Vercel org/project/token values, checks out the exact triggering SHA, pulls production configuration, builds with Vercel, deploys the prebuilt artifact and verifies health/hero/icon/greeting markers. It intentionally refuses to create a replacement project. G10 source/review gates PASS; the deploy gate remains BLOCKED because the audited Git publication channel and existing Vercel project binding are unavailable in the current environment.

## 9. n8n human-handoff contract

`integrations/n8n/cadre-handoff.workflow.json` is a credential-free optional adapter prototype. An isolated n8n 2.38.1 runtime proved import/publish/health plus local webhook behavior for valid lead/support requests and controlled consent/email failures. Routes are symbolic environment keys rather than real addresses. G11 is DONE at contract/runtime-prototype scope. The public chatbot is not wired to it, so no product copy may claim an email or CRM action was completed. If promoted, application code should depend on a `HumanHandoffProvider` capability rather than n8n-specific workflow details.

## Product and delivery boundaries

This assistant explains and redirects. It has no authentication, account-system access, portal session, verified public portal login URL, appointment creation, maturity-scoring engine, CRM, database or persistent chat store. Cadre's described portal may exist; the assistant does not connect to it. Published company capabilities and privacy statements are not promises that this chatbot performs them or inherits those guarantees.

The second-client fixture establishes tested separation at unit/integration level, not production reuse. Extractive fact ordering preserves approved context but can be repetitive and cannot supply unsupported answers. Process-local admission and budget bookkeeping are proportionate safeguards, not global availability or cost enforcement.

For current acceptance, use the [approved requirements](../specs/001-support-chatbot/requirements.md), [checkpoint](../progress/checkpoint.md), retained evidence and graph replay. Keep source/mock results, actual live evaluation, anonymous deployment verification, and clean archive extraction/build checks distinct. This inventory creates no claim that AC1, AC9, AC10, packaging, submission or final human closure has completed.
